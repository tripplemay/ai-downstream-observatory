# Controlled engineering verification

This runner executes fixed synthetic checks. It does not authorize investments,
place broker orders, certify a strategy, or promise returns. Public examples must
remain synthetic; personal plans, account facts and validation artifacts stay
in ignored local storage.

## Available check

`E-02.cash-contribution-neutrality.v1` is one engineering subcheck, **not full
E-02, G-03 or G-04 acceptance**. Every result carries:

```json
{
  "execution_authority": "controlled_runner",
  "data_provenance": "synthetic",
  "acceptance_scope": "engineering_subcheck"
}
```

Its result always has `gate_eligible: false` and `completed_requirements: []`.
The v1 gate-import interface does not accept a v2 job as formal gate evidence.
Legacy rows are neither rewritten nor upgraded.

The fixed child process creates a fresh temporary SQLite database using checked
migrations. It calls the normal Node ledger service for an opening CNY balance
of `100.25` and a subsequent deposit of `50.125`, then calls the actual Python
valuation and performance services. Expected NAV is `100.25 -> 150.375`, external
flow is `50.125`, and economic profit/return is zero. Independent Python and
TypeScript checkers reconstruct cash and flows with decimal arithmetic from
the recorded facts and postings rather than trusting the reported profit.

The two valuations are complete. Performance remains
`provisional / modified_dietz_estimate` with a linked return estimate and its
interval-flow/drawdown assumptions. It is not labelled exact TWR.

## Request and execution path

1. A logged-in human selects a portfolio at `/workbench/verifications`, reads
   the current context and supplies a reason. POST requires the current session
   binding and strict Origin. The server accepts only portfolio, fixed check ID,
   expected context hash, reason and idempotency key; callers cannot supply a
   command, path, environment, fixture, result or PASS claim.
2. One transaction records the immutable request, fixed system command, human
   audit and idempotent receipt. Requests bind the source manifest, check/suite
   version and portfolio, not the owner's funding plan or policy values.
3. Only `python -m worker.orchestration --role verifier` dispatches these jobs.
   Core and provider roles do not claim them. The verifier claims a fenced lease
   and runs a fixed isolated Python child and hash-bound Node bundle outside the
   final write transaction, with a clean environment, output/timeout limits,
   process-group cleanup, stop/recovery checks and lease heartbeats.
4. Under the same current lease, the final transaction verifies the request and
   source again, inserts the original artifact BLOB, independently checked
   result, execution/attempt binding and completion outbox event, then commits
   the terminal job state. Failed assertions produce `fail/failed`, not PASS;
   infrastructure failures retry without manufacturing an execution artifact.
5. Web reads revalidate the command, human audit, scope, attempt/fence, timestamps,
   terminal state, original bytes/hash, independent assertions and outbox.
   Invalid evidence is unavailable, not downgraded to a displayed PASS. Downloads
   return the original bytes as a fixed-name attachment after proof validation.

Restoration/read-only mode prohibits new requests and execution. Previously
verified evidence can still be read. Exact request replay retains its original
receipt; a changed actor/body with the same key is a conflict. History is
portfolio-scoped and keyset-paginated.

## Source identity and limits

`scripts/verification-source.mjs`, the TypeScript reader and the Python worker
independently enumerate the same explicit inventory: accounting, market,
orchestration, performance, research and verifier Python; server TypeScript;
contracts and migrations; and the fixed build/entrypoint/dependency files.
Symlinks, missing roots and an unlisted `worker/__init__.py` are rejected.

`npm --prefix web run build:verification-worker` generates:

- `web/dist/governance-fixture.mjs`
- `web/dist/governance-fixture.manifest.json`

The sidecar binds every inventoried source and the actual bundle SHA-256. Both
generated byte hashes are included in the request's source manifest. Source
changes require a rebuild and a new context; an old queued request cannot run
under changed source. Old execution evidence remains historical, with an
explicit current-runtime match indicator or unknown when source is unavailable.

Limits include 4,096 source files, 4 MiB per source, 1 MiB per artifact, strict
UTF-8/JSON, no duplicate keys, depth 64, safe integer JSON numbers and decimal
strings for financial values. Request identity/idempotency fields are bounded
ASCII; reasons are at most 1,000 Unicode code points.

This is **local controlled execution and build-integrity evidence**, not signed
remote attestation or a proof against an administrator who replaces the entire
application/database. It does not certify the complete release image, all
dependencies, all E/S cases or production behavior.

## Runtime and verification

Migration `0021_governance_verification_runner.sql` adds append-only request,
artifact and execution tables plus binding/terminal/unique-alias replacement
guards. Migrations 1-20 remain unchanged.

Web and worker images carry the same source inventory and generated fixture.
Compose runs a separate unprivileged verifier with `network_mode: none`, no
provider/auth env file, read-only root filesystem and a writable temporary
directory. Its shared database is used only for orchestration/evidence; the
synthetic financial ledger is created in a different temporary database.

Use a dedicated Python virtual environment with `requirements-workbench.txt`
installed, and set `WORKBENCH_TEST_PYTHON`/`WORKBENCH_PYTHON` when required:

```sh
npm --prefix web run build:verification-worker
python -m unittest discover -s tests/governance_verification -p 'test_*.py' -v
cd web
node --import tsx --test tests/verification-*.test.ts
npm run test:workbench:http
```

Tests cover normal TS request -> actual verifier execution -> independent TS
readback, failed assertions, atomic rollback, lease expiry/retry, process limits,
source mismatch, recovery and cross-scope/session boundaries. The independent
reader corruption matrix deliberately bypasses SQLite guards only in disposable
copies of a genuinely executed fixture; it never seeds a passing result.

Container smoke must independently compare both images' source manifests and
execute the same normal request/worker/proof path. Local unit results are not a
substitute for that image check, native browser QA or production acceptance.
