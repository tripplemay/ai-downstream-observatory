# 月度评估的证券审核知识边界

迁移 v20 修复同一时钟值内的证券审核更新进入原月度周期的问题。它不改变投资政策、证券审核原件、既有批准或真实账本，也不授予投资权限。

## 问题与原保护

服务器证券审核时钟来自毫秒时间并补齐为 UTC 六位小数。同一时钟值可能对应多个先后提交的审核版本。仅按 `known_at <= knowledge_at` 查询并取最大 revision，不能区别它们是否在周期建立之前已经存在。

v19 的单次准备/提交 hash 比较可以拒绝准备后的变化，既有交易批准也会因审核 proof 变化而失效；但新的准备或重试仍可能读取后来提交、时间恰等于周期知识点的版本。这个缺口不能只靠禁止相邻审核时间相等解决。

## v20 的冻结规则

- `listing_review_sequences` 为审核版本建立不可变整数序列。新版本与其序列由同一个 SQLite 写事务提交或回滚，不由用户、AI 或 Worker 载荷指定。
- `evaluation_listing_review_boundaries` 在新周期 INSERT 的同一事务中捕获该组合当前最大的审核序列，绑定周期、组合和原知识时间。没有审核时水位为 `0`。
- 月度历史选择同时满足原 `knowledge_at` 和冻结序列上界。全部目标、估值证券、实际持仓、在途证券和风险预留共享同一组合边界。
- 当前审核仍单独核验。即使当前时间等于原知识时间，也必须与原边界的审核 proof 一致；后写同刻版本不能偷偷进入原周期。
- 原边界纳入月度输入 manifest 和风险 hash；prepare、提交前重算以及人工重试均复用同一边界。缺原始审核仍是缺失，后来补齐不能把原周期改成当时已完整。
- 在周期创建前已提交、时钟值恰相等的合格审核仍可正常使用。无关证券更新不会无理由阻断未引用它的评估。

序列只能证明 SQLite 事务顺序。这里冻结的是“周期创建事务中已经存在、且声明的已知时间不晚于原知识点”的集合，不声称还原创建前同一毫秒内的物理时间顺序；补零也不意味着实际时钟具有微秒测量精度。

## 迁移与旧周期

迁移不改 v1-v19 SQL、原审核 wrapper、已有周期或 attempt 内容。已有审核建立确定性的迁移基线序列，该排列不被解释成历史提交顺序。

所有既有周期只追加 `legacy_missing` 边界标记，不用当前数据猜测其原水位：

- 已完成的输入、结果和 hash 继续可读，不重写旧证据。
- 待处理或重试旧周期返回 `EVALUATION_LISTING_BOUNDARY_MISSING`，不得补一个当前水位后宣称原周期成功。
- 后续正常创建的已授权月度周期自动获得边界。不得改旧周期、改策略名称或绕过周期唯一约束来伪造补跑。
- 如已独立满足现时建议的全部治理门槛，可按现有人工建议路径重新评估当前状态；该结果不是旧月度周期的补写成功记录。

普通证券审核 API、按时间的历史查询及非月度风险计算保持原语义；精确重放已完成月度评估时，应使用其存储的输入 manifest 和审核版本，而不是把一次新的时间查询当成旧快照。
