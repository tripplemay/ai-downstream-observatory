## 状态和已观察到的故障

恢复围栏基础、宿主机独立任务和工作流接线已实现。本地隔离测试通过，真正
Linux systemd 生命周期及准确 CI 仍待验证；不能称生产断连问题已修复，更
不能据此解除既有生产恢复锁。当前故障版本的续接不是重新运行这些新工具。

`75a7303` 的分支 push、PR、main CI 及独立发布验证各自完成 19/19。
但发布在恢复演练之后、新服务启动之前出现 `Connection reset by peer` /

这证明传输中断和当前切换进程耦合，不能仅凭断连推断网络设备或应用的根因。
现场恢复锁和停服状态已只读确认；原库及演练副本的 129 张相关表旧行一致，
3 个清单文件按各自角色核验，原库未回灌。生产续接需本次独立恢复确认。

## 已实现：先记录，再停写；先围栏，再清理

- `release-barrier.py begin` 在任何停写前独占创建 `cutover-started.json`，
  绑定精确 SHA、项目、实际数据目录和记录时点，文件及目录均完成 `fsync`。
  已有文件或持久化失败不是重试许可；不会继续停止旧写者。
- 创建意图前后保留恢复锁检查，落盘期间新出现的独立恢复标记仍阻断停写。
- `HUP`、`INT`、`TERM` 分别按 129、130、143 失败退出。停写前的失败保留
  旧服务；停写/迁移后的失败先建立恢复围栏，再执行可能阻塞的停止操作。
- 围栏只使用私有目录描述符和 `O_EXCL` / `O_NOFOLLOW` 创建，不跟随符号
  链接，不覆盖已有审核文字；已有硬链接、错误所有权或宽权限明确拒绝。
  CLI 只能由 root 操作，应用 UID/GID 固定，不能由参数选择。
- 不清除恢复锁，不恢复或改写原库，不增加任何备份，不调整数据用途、策略、
  资金、外发或交易权限。已有迁移、容量、身份、来源、健康和 current 门禁保留。

原实现的“停止之后再写锁”保护先红后绿；三类信号的停写前/后、晚到恢复锁、
写入失败、文件权限、链接及已有审核字节的行为各自执行。旧静态断言中的
停止后写锁顺序已改为更强的先围栏后停止；原停止和禁止回灌断言未删除。
本地相关套件通过 56/56。原根目录完整发现的 113 个测试文件执行 486 项，
485 通过、1 项原有可选跳过；1649 份跟踪代码及明确新增代码文件的前后哈希
一致，零跳过增加。集合有重叠，不相加。首轮旧顺序静态断言失败原件保留，
更新后完整重新执行；五个固定发布器、Bash 语法和 diff 检查通过。
这不是新 HTTP、Linux systemd、准确提交 CI 或生产验证。

## 已实现的独立任务协议：Linux 验证待完成，不替代当前恢复审批

宿主机已只读确认运行 systemd 255。官方描述的 transient **service** 由服务
管理器作为父进程，采用独立执行环境；`Type=exec` 能区别成功执行程序与仅
成功 fork。不得用仍继承调用端执行关系的 `--scope` 代替。
[systemd 255 官方源码文档](https://github.com/systemd/systemd/blob/v255/man/systemd-run.xml)

`scripts/release-job.py` 实现一次提交、只读观察的协议：

1. root 私有意图绑定 SHA、工作流 run/attempt、源清单、`release.env` 摘要及
   绝对期限；实际运行、行情与 AI 私有配置仍由原门禁分别核对。
   同 SHA 已有意图或任何未知结果都只允许查询，不自动重交，不重复备份。
   并发提交由私有全局文件锁串行化，另一未确认终态也阻断后续版本。
2. 受保护审核后才可提交宿主机 service；固定入口、`Restart=no`，不继承 SSH
   输入输出或凭据。取消 CI 观察者不等于停止已接收的切换任务，必须明确显示。
3. 沿用发布作业原 75 分钟总预算，期限在构建前建立，宿主机不重新起算。
   通过只读 Actions jobs API 取得原作业 `started_at`，增加的权限仅为
   `actions: read`；不是提交时重新给 75 分钟。耗时校验后再次检查剩余期限。
   [GitHub 官方 jobs API](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt)
   `RuntimeMaxSec` 和停止后处理共同约束，不用增大预算解决故障。
4. `ExecStopPost` 在异常退出后检查持久意图、实际服务及切换证据；不能证明
   停写前失败时，先围栏再停止对应项目写者。不得自动清锁、回灌或重启旧调度。
   成功还要求原切换成功记录、精确 current、源码与配置、实际健康角色、
   UID、OCI revision、已验证加载的实际 image ID 及只读 schema/外键核对。
   子进程退出 0、镜像标签、健康标签或自洽外层记录均不能单独放行。
   [systemd 255 service 官方文档](https://github.com/systemd/systemd/blob/v255/man/systemd.service.xml)
5. SSH keepalive 只是辅助；源归档准备仍是失败即停的独立步骤。仅短暂提交
   步骤允许观察者核对未知传输结果；源码校验、构建、审核和终态验证没有
   `continue-on-error`。提交异常原件保留，观察者绝不重新提交。
6. 终态独占落盘，状态查询同时读取实际 systemd handle；handle 仍在运行时
   即使终态文件已出现也不报告完成。handle 消失但无完整终态仍为未知，
   不把断线、查询超时或缺失状态判成成功。子进程只收到固定干净环境，
   不继承 SSH、模型、行情或云凭据。

作业目录先预留唯一身份；每份 JSON 在私有临时名下写全并同步，再以不覆盖的
原子 link 发布，避免读者看见半份 JSON。已知重复直接拒绝，不积累临时副本；
未知写入保留证据且不能自动重试。两项原子发布/重复保护均先红后绿。

状态接口只返回精确工作流绑定、期限和管理器状态，不返回配置、密钥、原始
日志或投资资料。作业目录只有少量私有意图/阶段/终态 JSON，不复制业务库、
价格或备份。它不提供删除状态、重试切换或清除恢复锁的命令。

Linux CI 必跑 `release-job-smoke.sh`：使用随机唯一假 SHA 的 root 私有新目录，
真实 PID 1 托管，终止模拟 SSH 调用者后确认原任务仍在运行，再让同一假任务
以停写前失败结束并核对只执行一次。它不调用 Docker、行情、网关或业务服务；
清理前检查 unit 的实际入口属于该目录，停止后验证 handle 终止才删除工装。
只有完成这一步后才输出 PASS，不以较早的成功行掩盖清理失败。
这不是完整成功切换、真实恢复或生产验收；本机 macOS 未运行该 Linux 步骤，
不能以单元测试替代它。缺少 Linux/systemd/sudo 时明确失败，不增加跳过。

新增 18 项本地协议/接线保护，相关套件 81/81：包括实际文件锁并发、提交未知、
重复 worker、源/配置/镜像变化、过期、凭据隔离、现有审核和链接保护、真实
SQLite 只读 schema 核对及不误停无关容器。首轮旧直接 SSH/bundle 接线断言
失败保留，已迁移到实际 host worker 的精确 bundle 路径检查，不删除原加载门禁。
最终完整根回归为 504 项：503 通过、1 项原有可选跳过（191.159 秒），114 个
原两层发现文件完整执行，1652 份跟踪/明确新增代码的前后哈希一致。五个固定
发布器、ShellCheck、39 段工作流 shell 语法及原生工装 Python 语法通过。
这些是本地证据，不是 systemd 原生/生产验收，也不是本轮重跑 Web/Python 全套。
